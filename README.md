## Мультимодальная диспетчерская система управления беспилотным транспортом (школьный проект)
## Что это

Мультимодальная[^1] диспетчерская система управления беспилотным транспортом (далее МДС), **согласовывающая маршруты автономного городского транспорта** нескольких типов:
[^1]: Мультимодальность — в данном случае это свойство системы работать с несколькими видами транспорта (модальностями), каждый из которых имеет собственную среду, правила и инфраструктуру, но при этом управляется в рамках единого диспетчерского контура. Для данной МДС признаками мультимодальности являются следующие выполняемые функции: обслуживает четыре вида транспорта с разными средами и графами, управляется единым диспетчером с общей картой занятости, обеспечивает межсредовое согласование в точках пересечения маршрутов, масштабируется добавлением новых модальностей без изменения ядра.

- тротуарные роверы;
- беспилотные автомобили;
- воздушные дроны;
- водные беспилотные суда.

МДС **не управляет** транспортом, но работает как «ГИБДД для дронов»: принимает заявки с планируемыми маршрутами от операторов автономного транспорта (далее АТ), проверяет их на конфликты с имеющейся информацией о движении АТ и транспортной ситуацией в целом и выдаёт разрешения.

## Зачем нужна

На сегодняшний день в крупных российских городах начинает использоваться появляется АТ в коммерческих целях. Уже сейчас по улицам движется множество беспилотных транспортных средств типа роверов, доставляющих заказы из интернет магазинов. Ожидается появление беспилотных автомобилей, поездов. Зарубежном развивается использование беспилотных летательных аппаратов, используемых службами курьерской доставки, транспортными компаниями, магазинами и т.д. Количество подобного транспорта постоянно растет. При массовом использовании АТ в городской среде без единого координатора возможны столкновения, взаимные блокировки, нарушение запретных зон.

Предлагаемая **мультимодальная диспетчерская система управления городским беспилотным транспортом** решает как минимум три основные задачи:

1. **Безопасность** — не допускать столкновений и появлений АТ в запретных зонах.
2. **Эффективность** — распределять маршруты избегая перегрузки коридоров движения и минимизируя влияния на транспорную систему города в целом.
3. **Обратная связь операторам АТ о текущей транспортной ситуации** — ремонты дорог, закрытые участки, мели на воде, разводные мосты и т.д.

## Как работает: цикл диспетчеризации МДС

```
Оператор АТ → Заявка в МДС → Проверка → Согласование → Движение АТ → Телеметрия от АТ → Актуализация маршрутов и другой информации
```

1. **Оператор АТ подаёт заявку** — начальная и конечная точка, предлагаемый маршрут, время вылета, тип транспорта.
2. **МДС проверяет** — пересечение с препятствиями, загруженность коридора, конфликты по времени.
3. **МДС выдает решение** — согласовано / согласовано с изменениями / отклонено (с рекомендациями).
4. **Согласованный маршрут** вносится МДС в **карту занятости** — он будет учитываться при согласовании последующих заявок.
5. **Оператор АТ собирает телеметрию** со своих АТ по собственным каналам и протоколам связи.
6. **Оператор АТ отправляет телеметрию** каждые 2–5 секунд: позиция, прогресс, ETA, статус, алерты в стандартизированном формате в МДС.
7. **МДС актуализирует информацию в своей базе** — сравнивает фактические координаты с плановыми для каждого маршрута, продлевает окна движения, отдает указания на перестройку маршрутов операторам АТ.

## Ключевые компоненты МДС

| Компонент | Назначение |
|---|---|
| **CityMap** | Препятствия: лестницы, перекопы, запретные зоны, мели, мосты |
| **Dispatcher** | Ядро: приём заявок, проверка, согласование |
| **OccupancyMap** | Карта занятости: какие маршруты где и когда активны |
| **Detector** | Детектирование отклонений: время, координаты, прогресс движения по маршруту|
| **Validator** | Проверка контракта телеметрии от клиентов |
| **Visualizer** | Карта города, временные окна, метрики |

## Четыре типа АТ — четыре группы препятствий, определяющих правила проверки и согласования маршрутов

| Тип АТ | Транспортная среда | Типовые препятствия |
|---|---|---|
| **Ровер** | Тротуары | Лестницы, узкие проходы, скопления людей |
| **Автомобиль** | Дороги | Перекопы, светофоры, закрытые полосы |
| **Дрон** | Воздух | Запретные зоны, эшелоны высот |
| **Катер** | Вода | Шлюзы, разводные мосты, мели, осадка |

## Формат файла телеметрии

Оператор АТ сам собирает данные со своих АТ и отправляет пакет в установленном формате (JSON):

```json
{
  "client_id": "pizza_shop_01",
  "batch_id": "batch-001",
  "vehicles": [{
    "vehicle_id": "rover_007",
    "route_id": "R-001",
    "position": {"x": 12.5, "y": 34.2},
    "status": "moving",
    "progress": 0.35,
    "eta": "2025-06-01T14:12:00Z",
    "alerts": []
  }]
}
```

МДС валидирует пакет по схеме, проверяет принадлежность маршрута клиенту и актуальность данных, после этого учитывает в базе данных.

## Что важно понимать

- **МДС — арбитр, а не пилот.** Он не строит маршрут за оператора АТ, а проверяет предложенный.
- **Каждое согласование влияет на следующие.** Это ключевая идея: карта занятости в базе данных МДС накапливает данные.
- **Обратная связь замыкает контур.** Без телеметрии система работает вслепую.
- **Архитектура масштабируема.** Новый тип транспорта = новый модуль проверки, ядро не меняется.

## Используемые программные технологии

Python 3.10+, Flask, Pydantic, Shapely, networkx, matplotlib, WebSocket.

## С чего начать новому участнику проекта

1. Прочитать документацию [https://github.com/bugaev-vs/mds-proto/tree/main/docs]
2. Ознакомьтесь `models.py` — базовые структуры данных.
3. Ознакомьтесь `dispatcher.py` — ядро логики.
4. Запустите `main.py` — увидите полный цикл на демо-сценарии.
5. Посмотрите результат работы программы, три графических файла: Городская карта, временные окна в форме графика Гантта, аналитические метрики.
